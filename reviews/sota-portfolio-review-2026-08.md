# State-of-the-art & portfolio review — 2026-08

**Scope:** DESIGN.md v3.1, DECISIONS.md (ADR-001…022), IMPLEMENTATION.md, ORCHESTRATION.md, reviewed against the 2025–2026 state of the art in LLM/RAG engineering, with the client's question in mind: *"are there buzzwords, hot topics, or state-of-the-art techniques we should be using that we currently don't?"*

**Portfolio context:** Rusty Data will use this open-source project to win LLM/RAG engineering work. The hosted product is non-commercial (load-bearing for licensing — nothing here proposes changing that; the Apache-2.0 *code* is the pitchable artefact, per ADR-018). Constraints held throughout: <£20/month hosting, small hand-audited corpus (~1–2M tokens), TDD methodology (IMPLEMENTATION.md), and the orchestration loop in ORCHESTRATION.md.

**Method:** full read of the four governing documents; web verification (August 2026) of the currency of each candidate technique where the picture may have moved since design time; verification of Anthropic API facts (citations/structured-outputs incompatibility, model pricing, prompt-caching minimums, Batches API) against current API documentation.

**Headline:** the design is already state-of-the-art in substance — hybrid retrieval with learned sparse, cross-encoder reranking, calibrated refusal, native citations, CI evals, severity-fidelity judging, fail-closed cost control. What it under-does is *naming* those techniques in industry vocabulary (Part A — near-zero effort, pure portfolio value), plus a small number of genuinely current additions, of which an **MCP server** is by far the highest visibility-per-effort (Part B). Several deliberate omissions are themselves portfolio assets when written up as reasoned rejections (Part C).

## Part A — Already used, under-branded

The design implements many techniques the industry has names for, but mostly describes them mechanically. A portfolio reader (a prospective client's CTO skimming the README) pattern-matches on the names. Recommendation: a "Techniques" section in the README (and interview talking points) that claims each by its industry term, linking to the section of DESIGN.md/DECISIONS.md that implements it. That section is one afternoon of writing and converts existing work into legible expertise.

Two vocabulary cautions:

- **Do not brand the sparse channel "BM25"** — ADR-007 already states this precisely; the correct claim is *learned sparse retrieval* (bge-m3's term weights are SPLADE-family), which is both accurate and more current.
- **Do not claim "hallucination-proof"** in any naming of A5/A7 — ADR-009's guaranteed-vs-measured split *is* the industry-facing differentiator ("we publish our groundedness numbers" beats "we can't hallucinate" in front of any technical buyer).

## Part B — Genuinely worth adding (with honest cost/benefit)

Verdicts: **ADOPT** (do in MVP or immediately post-MVP), **ADOPT-LITE** (minimal version now), **DEFER** (Phase 2+, real value but not now), **REJECT** (write up the rejection — feeds Part C).

### B1. MCP server exposing the corpus and charts — **ADOPT (highest portfolio leverage in this review)**

**What:** a read-only Model Context Protocol server exposing 3–4 tools: `search_corpus(query) → cited passages with attribution + deep links`, `get_passage(chunk_id)`, `render_chart(chart_spec | natural request) → permalink + PNG`, `list_datasets()`. Any MCP-capable client (Claude Desktop/Code, and by 2026 essentially every agent framework) can then ask grounded climate questions against our corpus and pull attributed charts.

**Why now:** MCP is *the* infrastructure story of 2025–26 — released Nov 2024, ~97M monthly SDK downloads by March 2026, ~41% of surveyed software orgs in production with MCP servers, a formal spec release cadence (2026-07-28 spec: stateless core, Tasks, MCP Apps), and even an NSA/CISA security advisory. For a consultancy selling LLM/RAG work, "we ship an MCP server" is the single most legible 2026 credential, and this project is unusually well-positioned: the retrieval function, chart renderer, permalinks, and attribution machinery all already exist as pure functions behind seams (IMPLEMENTATION §1) — the MCP server is a thin new shell over the existing core, exactly the architecture the TDD design was built for.

**Cost:** small. FastMCP (Python) over `rag/retrieve.py` + `charts/` is realistically 2–4 days including tests (the tools are deterministic wrappers; no LLM calls needed server-side if `render_chart` accepts a validated spec, and the search tool returns passages, not generations — the *caller's* model does the generating). Hosting: same box; MCP over streamable HTTP adds negligible load, and because the expensive step (generation) happens on the caller's side, **corpus search via MCP costs us ~$0/query** — it is budget-cap-friendly by construction.
**Risks/care:** (a) licensing — the MCP server redistributes retrieved text to arbitrary clients, so it must serve **Tier A (`permitted_context: open`) passages only**, enforced by the same structural filter pattern as the voices filter, with attribution strings in every response; length-bound excerpts exactly as the passages panel does. This is one manifest-keyed filter plus one deterministic eval. (b) Abuse — read-only tools, rate-limited, no state. (c) Non-commercial framing is unaffected: it's free public access to the same content by another transport.
**Minimal adoption:** Phase 2, first item; a single issue with a TDD plan (contract tests on tool schemas; structural licensing-filter test; replay test of one search round-trip). README badge + listing in the MCP Registry = visibility.

### B2. Anthropic contextual retrieval (LLM-generated chunk context) — **ADOPT (cheap upgrade of A4)**

**What:** replace/augment the current deterministic prepended header with a per-chunk, LLM-written 50–100-token context situating the chunk in its document (Anthropic's published technique: 35–49% retrieval-failure reduction, 67% combined with reranking; still widely cited as the 2026 baseline for production chunking).
**Why:** we already do the header-only variant, so the delta is small; the full variant is *Anthropic-branded* and we are an Anthropic-native stack — claiming "we implement Anthropic's contextual retrieval and measured its lift on our corpus with our published retrieval evals" is a strong, verifiable portfolio line. Our small corpus makes it almost free.
**Cost:** one Haiku call per chunk at ingest, ~2–4K chunks → single-digit dollars one-off, halved again via the **Batches API (50% discount, verified current)** since ingest is not latency-sensitive; with prompt caching on the full-document prefix it drops further. Ongoing cost: zero (ingest-time only). Engineering: a `contextualise(chunk, doc) → header` step behind the provider adapter, replay-tested; golden chunk fixtures change once, in one reviewed commit per the chunking guard.
**Care:** the generated context becomes part of the *embedded* text but must never be displayed as source text (it is not the source's words) — display keeps showing the verbatim chunk. Note for ND sources (Carbon Brief): generated context attached to a verbatim chunk is our text, not an adaptation of theirs, but keep it out of the displayed excerpt regardless; flag to the Phase-1.5 legal sanity-check for completeness.
**Gate:** it ships only if Recall@8/nDCG on the gold set improves — the A/B harness exists precisely for this. Even a null result is portfolio material ("we measured it; on a corpus this small with a reranker, headers sufficed").

### B3. Query expansion / HyDE / multi-query retrieval — **REJECT for MVP, evidence-backed (keep one narrow piece)**

**Verdict rationale (verified):** 2026 findings are consistent: query-expansion techniques help most when the first stage or reranker is weak; *"Beyond the Reranker"* (arXiv 2606.28367) reports limited headroom for expansion once a strong reranker is present, and HyDE specifically degrades on specialist corpora when the hallucinated document drifts off-corpus — plus every variant adds an LLM call of latency and cost to *every* query, against a £20/month budget. We already have the strong reranker and a query rewriter (DESIGN §3.1) that does the highest-value piece (reference resolution, acronym expansion). **Keep:** letting the existing rewriter emit *up to two* retrieval variants for genuinely ambiguous questions is a config-level tweak inside the existing structured-output call (no new call, ~zero cost) — worth an A/B experiment post-MVP, not an MVP feature. Write the rejection up (Part C flavour): "we measured our reranker first and declined to stack query-expansion latency on top" is a better consultancy story than cargo-culting HyDE.

### B4. Semantic / response caching for repeated public questions — **ADOPT-LITE**

**What:** before the LLM path, embed the (rewritten) query — an embedding we already compute for retrieval — and serve a cached answer when cosine similarity to a previously answered query exceeds a conservative threshold (~0.95+). 2026 production reports claim 40–86% cost reduction at high hit rates; for a public tool whose landing page *funnels users into ~14 starter questions*, the hit rate on a small set of canonical questions will be unusually high.
**Why LITE:** the design already pre-generates starter-topic answers for the paused state (§9). The lite version simply serves those same cached artefacts *during normal operation* on exact/near-match, extending existing machinery rather than adding a cache layer. That alone likely covers the bulk of repeat traffic at ~zero engineering cost beyond a similarity check, and stretches the daily budget (denial-of-wallet resistance improves too — ADR-015 synergy).
**Care (why not full semantic caching of arbitrary answers):** the classic failure is serving a cached answer to a *similar but different* question — for an anti-misinformation product that is a real integrity risk. Hence: conservative threshold, cache keyed on corpus version + prompt version (invalidate on either), cached answers carry their generation date, and a small eval subset of near-miss question pairs that must *not* cache-hit. Full arbitrary-answer caching: defer until logs show repeat-query mass outside the starter set (the logs the design already keeps will answer this).
**Portfolio line:** "semantic response caching with integrity-gated thresholds" — a named 2026 technique, honestly scoped.

### B5. Observability / tracing (Langfuse, OpenTelemetry GenAI) — **DEFER confirmed, with one nuance (verified)**

The design defers Langfuse (§8) in favour of structured JSON logs. **Verified August 2026: the OTel GenAI semantic conventions are still *not* stable** — as of June 2026 they were moved to a dedicated repo (`semantic-conventions-genai`), all docs remain "Status: Development", no tagged release, no stabilisation timeline. So the deferral is not a gap; standardising now would mean chasing a moving target. **Nuance worth one line of code:** shape the existing JSON log fields (`gen_ai.request.model`, `gen_ai.usage.input_tokens`, span-per-pipeline-stage naming) *after* the current draft conventions so a later Langfuse/OTel adoption is a transport change, not a schema migration — and say so in the README ("OTel-GenAI-aligned structured logs; full tracing deferred until the conventions stabilise"). That sentence is itself a portfolio signal: it shows we track the standards process rather than name-dropping it.

### B6. Agentic RAG / query decomposition for multi-hop questions — **DEFER (post-MVP experiment, narrowly scoped)**

**Verified 2026 picture:** "agentic RAG" is the year's dominant RAG buzzword, but production reports are consistent that reflection/decomposition loops cost 3–10× the tokens of single-shot RAG and pay off only on genuinely multi-hop workloads; the recommended path is "advanced RAG first, agent on top only where evals prove the need". Our pipeline *is* the "advanced RAG" baseline, and our corpus is small and coherent — most briefing questions are single- or dual-passage (the gold set's ~10 multi-passage items measure exactly this). **Minimal adoption when warranted:** if multi-passage Recall@8 underperforms at MVP, add *bounded* decomposition — the existing scope classifier flags `multi_hop`, the rewriter emits ≤3 independently retrievable sub-queries, results merge before the same rerank/refusal/generation path. No loops, no tool-calling agent, one extra structured call only on flagged queries. Cost-bounded, testable, and honestly describable as "selective query decomposition", which is the defensible 2026 position. Do not brand the current product "agentic" — it isn't, and technical buyers notice.

### B7. GraphRAG — **REJECT (write the rejection up)**

Knowledge-graph-augmented RAG earns its cost on large, entity-dense corpora where multi-hop reasoning across *documents* dominates (enterprise wikis, litigation discovery) and where someone will pay the graph-construction and maintenance bill. Our corpus is ~1–2M tokens of *assessed synthesis documents* — the cross-document weighing GraphRAG tries to recover is already done by the IPCC/NCA5 authors; that is precisely why ADR-002 chose assessed literature. Graph extraction would add an LLM-heavy ingest stage, a second store, new failure modes (hallucinated edges in an anti-misinformation product), and no measurable benefit on a corpus this small and this curated. Reject with confidence; it makes an excellent "we know when *not* to" portfolio paragraph (Part C).

### B8. Late chunking / ColBERT-style late interaction — **REJECT at our scale (one sentence of nuance)**

Late-interaction retrieval (ColBERT/PLAID) and late chunking trade index size and infra complexity for recall gains that matter at large scale or when chunk boundaries destroy context. We already mitigate the boundary problem twice over (structure-aware chunking + contextual headers, upgraded by B2), and we already run a cross-encoder over the candidates — which is a strictly stronger interaction model applied where it is cheap (top-40 only). Amusing footnote worth keeping for interviews: **bge-m3 natively emits ColBERT multi-vectors that we deliberately leave unused** (ADR-005 notes this) — the rejection is a config choice away from being falsifiable, which is the strongest kind of rejection.

### B9. Embedding quantization — **REJECT (trivially unnecessary; know the numbers)**

Binary/int8 quantization exists to cut memory and cost at 10⁷–10⁹-vector scale. Our index is ~thousands of chunks — the full-precision index fits in memory hundreds of times over on the £20/month box. Adopting it would save nothing measurable and add a recall-loss risk we'd then have to eval. The portfolio-correct move is to *know* the technique and state why it's out of scope ("we'd reach for binary quantization + rescoring at ~10M vectors; at 5K it is cargo cult").

### B10. RAGAS / DeepEval vs our custom harness — **KEEP custom core (per ADR-014), ADOPT-LITE a comparability layer**

**Verified 2026 picture:** RAGAS remains the standard *vocabulary* for RAG metrics (faithfulness, answer relevancy, context precision/recall); DeepEval has become the "pytest for LLMs" CI-testing framework; many teams run both. ADR-014's reasoning still holds — our novel metrics (citation-support against native-citation blocks, calibrated-term preservation, severity fidelity, chart data faithfulness) do not exist off the shelf, and they are the differentiator. **The lite adoption:** (a) *report* our metrics using RAGAS-standard names where they coincide (our faithfulness judge ≈ RAGAS `faithfulness`; our Recall@8 ≈ `context_recall`) so `evals/RESULTS.md` is legible to anyone fluent in the standard framework; (b) optionally run RAGAS once per release on the gold set as a comparability column (~an afternoon; it's a library call over run records we already produce). This converts "custom harness" from a possible red flag ("did they NIH their evals?") into a strength ("custom metrics for the product's actual promises, cross-reported in standard vocabulary").

### B11. Guardrails frameworks (NeMo Guardrails, Guardrails AI, Llama Guard) vs bespoke — **KEEP bespoke, document the comparison**

Our guardrails are mostly *structural* (code-enforced filters, renderer-enforced chart integrity, manifest-enforced licensing) — a category the frameworks don't cover — plus a scope classifier we need anyway for routing. A rails framework would add a dependency and a DSL to reimplement what four pure functions already do testably (IMPLEMENTATION §1 lists each as a seam). The one thing frameworks buy — maintained jailbreak/unsafe-content classifiers — we cover with the canned-response unsafe path and the adversarial eval set, proportionate to a read-only public Q&A tool with no actions or PII access. Write one README paragraph mapping our layers onto the frameworks' taxonomy (input rails = scope classifier; output rails = citation-support validator; retrieval rails = voices filter; execution rails = ChartSpec validator). That paragraph *is* the portfolio artefact.

### B12. DSPy / GEPA prompt optimisation — **DEFER (one bounded experiment, post-MVP)**

**Verified:** GEPA (reflective prompt evolution; ICLR 2026 oral) is the current state of the art in prompt optimisation and DSPy remains its main vehicle; real production users (e.g. Decagon) report meaningful gains optimising *judge* and *classifier* prompts. We have exactly the right substrate: small, well-defined structured-output tasks (scope classifier, chart planner) with deterministic gold-set metrics to optimise against. **But**: our prompts are load-bearing, hand-audited artefacts; replay fixtures invalidate on prompt change *by design*; and an optimiser in the loop conflicts with the TDD discipline unless bounded. Minimal adoption: one offline experiment, post-MVP — GEPA over the scope-classifier prompt against classifier accuracy on the gold set, budget-capped, result committed as a findings note whether or not it ships. High interview value ("we ran GEPA on our classifier; here's the delta"), zero MVP risk.

### B13. Synthetic eval-data generation — **DEFER (already correctly reasoned in ADR-014), with one addition**

ADR-014's position stands: 75 hand-built questions with gold chunk-ids beat 400 unvetted synthetic ones on a corpus this small, and severity annotation is inherently human. One cheap addition worth taking now: use an LLM to generate *paraphrase variants* of existing gold questions (not new questions — same gold chunk-ids, same expected answers) as a robustness set for the retrieval metrics. This is synthetic data where it is safe (question surface form) and not where it is dangerous (answer/severity ground truth). ~Half a day; gives a "robustness to phrasing" number the RESULTS page can publish.

### B14. Online evaluation / user-feedback loop — **ADOPT (small, high-value, already half-designed)**

The design logs every exchange as "a future eval case" (§8 observability) and defines the harvest pipeline (hand-review, detachment from timestamps/IPs, GDPR §9). What's missing is the *signal*: a thumbs up/down (plus optional "what's wrong?" categories: wrong/unsupported/too alarmist/too reassuring/refused wrongly) on each answer, and the badge-click on "unverified" citations counted as implicit signal. Down-voted exchanges jump the harvest queue and become candidate gold-set items via the existing review pipeline; per-release dashboards of feedback rates join `evals/RESULTS.md`. Cost: one UI widget, one log field, one triage script — days, not weeks. This is the industry's "online evaluation / continuous evals" story and it closes the loop the architecture already anticipates; note the two severity-complaint categories map directly onto the severity-fidelity scale, making triage cheap. GDPR posture is unchanged (feedback is another field on an already-governed log record; the disclosure line should mention it).

### B15. A/B infrastructure (online) — **DEFER**

Offline A/B exists (§6.3) and is the right tool at our traffic levels. *Online* A/B (traffic splitting, e.g. landing-page framing variants, which §1 explicitly plans to test post-launch) needs enough traffic for significance and adds assignment/analytics machinery that rubs against the no-identifiers privacy posture (bucketing can be done with the existing salted-IP hash, but power will be the binding constraint). Revisit when traffic justifies it; until then the honest claim is "offline A/B on every pipeline change; online experiments deferred pending traffic".

### B16. Additional current items the brief didn't list

- **Anthropic Batches API for judge runs — ADOPT.** Verified: 50% discount, ≤24h turnaround, all Messages features supported. Release-gate judge runs (faithfulness, severity, adversarial rubric — §6.2) are batch-shaped by definition. Halves the per-release eval spend for one adapter method (`structured_batch(...)`), and "we run our eval gates on the Batches API at half cost" is a nice operational-maturity detail. - **Prompt-caching hygiene — fix before claiming A12.** See finding F2 below: the cost model's caching assumption has a silent failure mode worth one design note and one test.

## Part C — Deliberately not used: the defensible-rejection list

Each of these is a one-paragraph "we know it, we measured the trade, we declined" statement — collectively they may be worth more to a technical buyer than the feature list, because they demonstrate judgement, which is what a consultancy sells. Suggested home: a "What we deliberately don't do" section in the README, each paragraph linking its ADR.

**C1. Fine-tuning a "climate model" (ADR-004).** We do not train or fine-tune on climate text. Fine-tuning teaches style and distribution, not attributable facts: parametric knowledge cannot be cited, cannot be updated without retraining, and flattens the IPCC's calibrated language ("very likely") into the model's own confident register — the precise failure this product exists to prevent. It would also reproduce the licensing problem inside the weights, where no manifest can govern it. Retrieval keeps knowledge where it can be inspected, versioned, licensed, and refused. The one fine-tune we would consider — a domain-tuned *embedding* model, once eval data proves a gain — is noted in ADR-004 as a plausible later experiment, which is the correct scope.

**C2. Open web search (ADR-021).** An anti-misinformation tool that charts or cites whatever a search engine returns has imported its adversary's supply chain: unvetted claims, unknown licences, and a prompt-injection vector, all breaking the "every pixel from named datasets, every claim from audited sources" guarantee. We refuse honestly, name the nearest available dataset, log the gap, and grow the corpus demand-driven with a human in the loop; Phase 2 adds fetch from an *allowlist* of trusted providers with schema validation and a "not yet curated" label. Currency comes from corpus releases, not crawling.

**C3. LLM code generation for charts (ADR-020).** The model writes a ~1 KB declarative ChartSpec over a closed, code-validated vocabulary; our renderer makes the pixels. No generated code ever executes: this eliminates the injection sandbox problem entirely, makes every chart reproducible from its spec hash, and lets chart-integrity rules (labelled baselines, full-range defaults, mandatory splice annotations) live in the validator where the model cannot negotiate with them. Flexibility is bounded by design — requests outside the vocabulary get an honest refusal — and the vocabulary grows by code review, not prompt engineering.

**C4. GraphRAG (this review, B7).** Entity-graph construction pays off on large, fragmented corpora where cross-document multi-hop reasoning must be recovered mechanically. Our corpus is small, hand-audited, and consists of *assessment* literature whose entire purpose is that experts already did the cross-document synthesis. A graph layer would add an LLM-heavy ingest stage, a second store to operate under £20/month, and a new hallucination surface (extracted edges) — to solve a problem our source selection already solved.

**C5. RAG frameworks — LangChain/LlamaIndex (ADR-016).** The pipeline is ~300 hand-rolled, heavily unit-tested lines because the interesting parts — statement-ID chunking, custom-content citation blocks, reranker-thresholded refusal — are exactly the layers frameworks abstract away. For a public portfolio codebase, framework indirection makes the showcase *harder* to read; hand-rolling was less code than configuring around a framework's opinions. Where RAG is a commodity feature rather than the product, we'd say the opposite — and do, in the ADR.

**C6. Managed vector databases and API embeddings (ADR-005/007).** Embeddings and reranking run locally (bge-m3 family) and the store is OSS Qdrant, because our published eval numbers must be reproducible forever: a vendor retiring an embedding model silently invalidates a published retrieval eval. At ~5K vectors, managed scale buys nothing; open weights pinned by revision buy permanence. At 100M+ vectors or real QPS, the calculus flips — stated in the ADRs.

**C7. "Can't hallucinate" claims (ADR-009).** Native citations guarantee that citations resolve to real retrieved text; they do not guarantee entailment. So we split the claim: resolution is *guaranteed by construction*, entailment is *measured and published* per release, with runtime "unverified" badges as the honest backstop. An epistemic-honesty product that overclaims its own epistemics is self-refuting; publishing our failure rates is both the intellectually consistent position and the rarer, more credible pitch.

**C8. Broad web corpus / primary papers at scale (ADR-002).** RAG faithfully repeats its corpus, so corpus curation is the first guardrail: only assessed, consensus-grade, clearly-licensed publications are admitted, small enough to hand-audit every document. Contested material (the denialist myth taxonomy) informs the *adversarial eval set*, never the corpus. More refusals, honestly handled, beat one confidently cited bad source.

**C9. Local/open-weight generation for the MVP (ADR-012).** The headline behaviour — mechanically verifiable citations — is an Anthropic API feature; small local models are measurably worse at exactly our failure mode (subtle unfaithfulness, qualifier drift), and GPU hosting breaks the budget worse than Haiku does. The coupling is contained behind a provider adapter with a designed (marker + entailment-gate) fallback, so the local path stays credible without being built prematurely.

**C10. Query expansion / HyDE at MVP (this review, B3).** With hybrid retrieval and a cross-encoder reranker in place, 2026 evidence shows limited headroom for query-expansion stacks, and HyDE specifically risks off-corpus drift on specialist material — while adding an LLM call of latency and cost to every query. We spend that budget on the reranker and refusal gate instead, and hold multi-query as a measured post-MVP experiment inside the existing rewriter call.

**C11. Agentic branding without agentic substance (this review, B6).** The pipeline is a fixed, auditable DAG, not an agent loop — deliberately: bounded cost per query (a hard requirement under a fail-closed cap), bounded latency, and behaviour that can be regression-tested. Decomposition will be added *selectively* if the multi-hop evals demand it. We call things what they are; technical buyers notice.

## Findings that touch the design's current assumptions (verified August 2026)

- **F1 — Citations × structured outputs incompatibility: still true.** Current Anthropic docs confirm citations remain incompatible with structured outputs (400). The separate-calls architecture (§3.1/§3.4, ADR-008) and its contract tests remain necessary. Also confirmed: `claude-haiku-4-5` $1/$5 and `claude-opus-4-8` $5/$25 per MTok — the §9 cost model's prices are current. (Note the top-level `output_format` parameter has been deprecated in favour of `output_config.format` — an implementation detail for issue #24's request builders, not a design change.)
- **F2 — Prompt caching has a minimum-prefix gotcha the cost model doesn't mention.** On current models the minimum cacheable prefix for Haiku 4.5 is **4096 tokens**; shorter prefixes silently don't cache (no error — `cache_creation_input_tokens: 0`). Our per-query input is ~5–6K tokens but most of that is the *per-query* retrieved top-8, which never caches; only the static prefix (system prompt + any fixed blocks) is cacheable, and if it is under ~4K tokens the "less with prompt caching" assumption in §9 silently yields zero. Action: either size/order the static prefix accordingly (system prompt + likelihood legend + fixed instructions first, volatile content after the breakpoint) or drop the caching discount from the cost model; add a smoke check that `cache_read_input_tokens > 0` on the second replayed request. Cost impact is small in absolute terms (~$1–3/month at 1K queries) but the design should not claim a mechanism that may not be firing.
- **F3 — OTel GenAI semantic conventions are NOT stable (as of July 2026)** — moved to a dedicated repo, all "Status: Development", no tagged release, no stabilisation timeline. The design's deferral of Langfuse/tracing is validated; align log field names with the draft conventions now (B5) but do not claim conformance to a stable standard.
- **F4 — Batches API: 50% discount on all token usage, ≤24h.** Unclaimed saving for release-gate judge runs and for the B2 contextualisation pass (both batch-shaped). No design change required beyond one adapter method.
- **F5 — Query-expansion headroom with strong rerankers is limited** (arXiv 2606.28367 and consistent 2026 practitioner reporting) — turns our B3 rejection from opinion into an evidence-backed position; cite it when writing the C10 paragraph.
- **F6 — MCP has crossed from buzzword to infrastructure** (spec RC 2026-07-28; ~97M monthly SDK downloads; NSA/CISA security guidance exists) — strengthens B1 from "nice demo" to "table-stakes credential", and the security-advisory existence is itself useful: our read-only, Tier-A-only, rate-limited design answers the questions that advisory teaches buyers to ask.

## Top-5 recommendations, ranked by portfolio-value-per-effort

1. **B1 — Ship a read-only MCP server** (corpus search + attributed chart rendering, Tier-A-only, structurally filtered). Days of work over existing seams; the single most legible 2026 credential a RAG consultancy can hold, and ~$0/query by construction.
2. **A1–A18 — Claim what we already do, by name.** A README "Techniques" section + "What we deliberately don't do" (Part C paragraphs). One or two days of writing; converts an already state-of-the-art design into *visibly* state-of-the-art marketing with zero engineering risk.
3. **B2 — Full Anthropic contextual retrieval at ingest** (LLM-generated chunk context, Batch-API-priced, single-digit dollars one-off), gated on measured retrieval-eval lift via the existing A/B harness. Anthropic-branded technique on an Anthropic-native stack, with published before/after numbers either way.
4. **B14 — Thumbs up/down wired to the eval harvest** (online evaluation loop). One widget + one log field + a triage script; closes a loop the architecture and GDPR section already anticipate, and "continuous evaluation from user feedback" is a first-class 2026 talking point.
5. **B4 — Semantic response cache over the starter-topic answers** (conservative threshold, corpus-version-keyed, near-miss eval items). Extends the existing pre-generation machinery into a named technique ("semantic caching"), stretches the £20 budget, and hardens the denial-of-wallet posture.

*(Freebies not ranked: F4 Batches API for judge runs; B16 `llms.txt`; F2 prompt-caching prefix fix; B5 OTel-aligned log field names — each under a day, all worth doing.)*

**Single highest-leverage change overall: the MCP server (B1).** Everything else in this review polishes or extends an already-excellent RAG design; the MCP server changes what the project *is* in a buyer's eyes — from "a well-built RAG chatbot" (a crowded 2026 category) to "a grounded climate-knowledge service any agent can consume" (a current, scarce, and demonstrably 2026-native artefact), at a cost the existing pure-core architecture has already paid for.
